Build your first skill

A working skill, end-to-end, in under ten minutes. We'll build commit-classifier — a skill that reads git diff --cached and writes a conventional-commit message.

Step 1 — Decide what the skill does

Before writing any code, answer four questions in one sentence each:

  • Trigger: When should Claude invoke this skill? ("When the user asks Claude to write a commit message after staging changes.")
  • Inputs: What does it need? ("The output of git diff --cached and the project's prior commit style.")
  • Output: What does it produce? ("A conventional-commit message printed to the chat, optionally written via git commit -m.")
  • Tools: What permissions does it need? ("Bash to run git, that's it.")

If you can't answer all four in one sentence, the skill is doing too much. Split it.

Step 2 — Create the folder

mkdir -p ~/.claude/skills/commit-classifier/scripts
cd ~/.claude/skills/commit-classifier

Folder name = skill name = the name field in frontmatter. Lowercase kebab-case throughout.

Step 3 — Write SKILL.md

This is the entire skill. Frontmatter on top, instructions below.

---
name: commit-classifier
description: |
  Write a conventional-commit-style commit message from the currently staged
  diff. Triggers when the user asks Claude to "write a commit message",
  "what should I name this commit", or "/commit" after running git add.
  Inspects git diff --cached, classifies the change, and produces a tight,
  project-style message.
allowed-tools:
  - Bash
  - Read
version: 0.1.0
---

# commit-classifier

When this skill activates:

1. Run scripts/inspect.sh to gather:
   - The staged diff (git diff --cached)
   - The last 10 commit messages (for project style)
   - The list of staged paths (for scope inference)

2. Classify the change into one of:
   feat | fix | refactor | docs | test | chore | perf | style | build | ci

   Use this rubric:
   - feat: net-new user-facing capability
   - fix: corrects a bug or unintended behavior
   - refactor: internal-only restructuring, no behavior change
   - docs: only .md / comment / README changes
   - test: only test-file changes
   - chore: deps, lockfiles, version bumps

3. Pick a scope from the changed paths. Prefer the deepest directory
   shared by >50% of changed files (e.g., auth, api/users).

4. Write a subject line:
   - Imperative mood ("add", not "added")
   - Under 60 characters
   - No trailing period
   - Format: <type>(<scope>): <subject>

5. Print the message in a code block. Do NOT run git commit
   yourself unless the user explicitly asks you to.

## Examples

Good:
- feat(auth): add WebAuthn passkey enrollment
- fix(api/users): handle null email on social signup
- refactor(db): collapse user + session loaders

Bad (and why):
- "Update files" — no type, no scope, no signal
- "feat: lots of changes" — vague subject
- "feat(auth): added new login flow." — past tense, trailing period

Step 4 — Add a helper script

Anything deterministic should live in a script, not in the markdown. It saves tokens, runs the same every time, and is testable on its own.

# scripts/inspect.sh
#!/usr/bin/env bash
set -euo pipefail

echo "=== Staged paths ==="
git diff --cached --name-only

echo
echo "=== Staged diff ==="
git diff --cached --stat
git diff --cached

echo
echo "=== Recent commit messages ==="
git log -10 --pretty=format:"%s"
chmod +x scripts/inspect.sh
Why a script? A 30-line shell file is faster, cheaper, and more reliable than getting the model to assemble three git invocations correctly every time. Skills get better when you offload determinism to code.

Step 5 — Test the trigger

Open a fresh Claude Code session in a repo with staged changes and try variations:

  • "Write a commit message for what I just staged" → should activate
  • "What should I name this commit?" → should activate
  • "Help me think about my architecture" → should not activate

Watch the transcript for the skill-loaded notification. If the skill doesn't activate when you expect, your description is too narrow. If it activates when you don't expect, it's too broad.

Step 6 — Iterate on the description

This is where 80% of skill quality comes from. Tighten the description in passes:

  • Pass 1 — Trigger phrases. List the exact phrases users say. Quote them in the description.
  • Pass 2 — Negative scope. If you're getting false positives, add "Does NOT apply to X" sentences.
  • Pass 3 — Input shape. Mention attached files, staged state, current branch — whatever context clues separate this from related skills.

Step 7 — Package & publish

To share with teammates, commit the folder to a public or private repo:

cd ~/.claude/skills/commit-classifier
git init
git add SKILL.md scripts/
git commit -m "Initial commit-classifier skill"
gh repo create my-team/claude-commit-classifier --public --source=. --push

Teammates install with:

git clone https://github.com/my-team/claude-commit-classifier \
  ~/.claude/skills/commit-classifier

For wider distribution, submit a PR to a community skills index (github.com/topics/claude-skills) so it shows up in searches.

Skill with Bash + bundled script

---
name: my-skill
description: Trigger phrase, more phrase, action verb describing what it does.
allowed-tools:
  - Bash
  - Read
---

# My Skill

1. Run scripts/run.sh to gather inputs.
2. Decide based on output.
3. Report back to the user.

Skill with multi-step lookup table

---
name: api-error-helper
description: |
  When the user pastes an HTTP error response from our API or asks
  "what does error X mean", look up the code in reference/errors.md
  and walk through the documented remediation.
allowed-tools:
  - Read
---

# API Error Helper

1. Find the error code in reference/errors.md.
2. Quote the description and the listed remediation steps.
3. If the code is not listed, say so explicitly. Do not guess.

Pre-publish checklist

  • [ ] name matches the folder name (kebab-case)
  • [ ] description includes 2+ concrete trigger phrases
  • [ ] allowed-tools is the minimum needed — no extra Bash / Write
  • [ ] Scripts have an execute bit (chmod +x)
  • [ ] Heavy reference content is in reference/*.md, not inlined
  • [ ] Tested with three positive trigger phrases and two negatives
  • [ ] Tested in a fresh session, not just the one where you built it
  • [ ] README explains what the skill does, install command, and version compatibility
  • [ ] LICENSE file (MIT, Apache-2.0, or BSL — pick one)
One more thing. The skill-creator skill in the official repo will scaffold all of this for you. Install it once, then say "create a new skill that does X" — it'll generate the folder, write the frontmatter, and remind you of the checklist above.
