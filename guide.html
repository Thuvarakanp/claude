How Claude Skills work

Skills are Anthropic's answer to the question: "how do I give Claude a new capability without bloating every prompt with instructions for it?". Read this once and the rest of the system makes sense.

1. What a skill actually is

A skill is a folder. That folder contains:

  • One required file: SKILL.md, with YAML frontmatter on top and free-form markdown below.
  • Zero or more bundled assets — scripts, templates, reference docs, schemas — that the skill body refers to.

That's it. There's no compilation step, no runtime, no JavaScript framework. A skill is a piece of documentation Claude reads, plus some files it can choose to open or execute while the skill is active.

Concretely:

pdf/
├── SKILL.md
├── scripts/
│   ├── extract_text.py
│   ├── fill_form.py
│   └── merge.py
└── reference/
    ├── form_fields.md
    └── pypdf_cheatsheet.md

2. Why skills exist (vs. system prompts)

You could teach Claude how to fill PDF forms by jamming five pages of pypdf docs into the system prompt. That has three problems:

  1. Bloat: every prompt pays the token cost, even ones that have nothing to do with PDFs.
  2. Distraction: a giant system prompt makes Claude worse at unrelated tasks.
  3. Lock-in: the capability is welded to one product / one team's prompt — not portable.

Skills solve all three. They're portable (a folder you can move between surfaces), lazy (only loaded when relevant), and composable (combine many in one session without exploding context).

Mental model: a system prompt is everything Claude is told up front. A skill is a capability Claude opts into when the conversation calls for it.

3. Progressive disclosure

The killer design choice. Claude doesn't see your skill's full body unless it decides to use it.

StageWhat Claude seesWhen
DiscoveryOnly frontmatter — name + descriptionAlways, for every installed skill
ActivationFull SKILL.md bodyWhen the user's prompt matches the description
Drill-downBundled files (scripts, reference, templates)When the skill's body says "see reference/form_fields.md"

This is why you can install 50 skills without context bloat. Until one triggers, Claude only spends tokens on the descriptions — typically a sentence each.

4. Frontmatter reference

---
name: string                # required, kebab-case, matches folder name
description: string         # required, ~1 sentence, drives triggering
allowed-tools: list          # optional, default: inherit session tools
  - Read
  - Write
  - Bash
model: string                # optional, override model for this skill
version: string              # optional, semver
author: string               # optional
license: string              # optional, SPDX id
---
  • name — must match the folder name. Lowercase kebab-case.
  • description — written for the model, not for humans. Lead with when to use the skill, then what it does. Concrete trigger phrases (in quotes) help a lot.
  • allowed-tools — restrict the skill to a subset of session tools. Useful for safety: a "render HTML" skill shouldn't need Bash.
  • model — pin a specific model for this skill. Rare, mostly for cost-sensitive workflows that don't need Opus.

5. How triggers work

There's no regex. There's no keyword list. When the user sends a message, Claude reads the descriptions of every installed skill and picks the ones that look relevant. That's it.

This is why the description matters so much. Bad descriptions never trigger. Good ones trigger reliably without false positives.

A bad description

description: Helps with files.

A good description

description: Extract text and form-field values from PDF documents, fill
  interactive PDF forms from JSON or CSV data, merge or split PDFs, and generate
  new PDFs from markdown. Triggers on phrases like "fill this form", "extract
  from PDF", "merge PDFs", or when a .pdf file is attached.
Rule of thumb: if a teammate could read the description and know exactly when to invoke the skill, Claude can too. If the description is vague to a human, it'll be vague to the model.

6. allowed-tools and trust

Skills can scope down which tools they're allowed to call. This protects you from a skill that drifts in scope — a "summarize this doc" skill has no business calling Bash.

If allowed-tools is omitted, the skill inherits whatever the session already has. If it's present, the listed tools are the maximum — the skill can never exceed them, even if the session is more permissive.

For high-trust skills (anything that writes to disk, calls the network, or executes scripts), pair allowed-tools with explicit per-script permission prompts in your settings.json.

7. Composing multiple skills

Skills layer. A single user prompt can activate several:

  • "Generate a financial-projection deck from this Excel file" → activates xlsx (read the data), data-viz (build the charts), pptx (write the deck), and web-design (apply tasteful styling).
  • "Push the auth page design into Figma" → activates figma-use (mandatory pre-flight) and figma-generate-design (the actual push).
  • "Review my branch for security issues" → activates security-review, which under the hood pulls in github-pr-ops if there's an open PR.

Skills don't communicate with each other directly. They each contribute instructions to Claude's working memory, and Claude orchestrates the result.

8. Skills vs. slash commands vs. MCP vs. memory

FeatureSkillsSlash commandsMCP serversMemory
What is it? A folder of instructions + assets Claude loads on demand A user-typed shortcut to a prompt template A long-running process exposing tools / resources via a protocol Persistent facts that stay across sessions
Triggered by The user's natural language matching the description The user typing /name Claude calling one of its tools Recalled when relevant to the current task
Lives where? ~/.claude/skills/ ~/.claude/commands/ External process, registered in settings.json ~/.claude/memory/
Best for Capabilities (write Excel, run review) Workflows (open standup template) Integrations (talk to Postgres, Slack, Linear) User/project facts, preferences, history

These layer happily. A skill can call MCP tools. A slash command can suggest a skill. Memory can remind Claude that a skill exists.

9. Skill lifecycle in a session

  1. Session start: the loader scans ~/.claude/skills/ and .claude/skills/, parses each SKILL.md frontmatter, and registers the (name, description) pairs.
  2. User sends a prompt: Claude sees the prompt + all registered (name, description) pairs.
  3. Selection: Claude decides one or more skills are relevant and silently loads their full SKILL.md bodies.
  4. Execution: the skill body becomes part of Claude's working memory. It may call tools, read bundled files, or write outputs.
  5. Hand-off: as the conversation evolves, irrelevant skills "fade" — their content is not actively referenced. New skills can activate later in the same session.

10. Best-practice patterns

  • One job per skill. A skill called "do-everything-with-pdf" is harder to trigger reliably than three skills for fill / merge / extract.
  • Front-load the description. Put trigger phrases in the first sentence, not buried.
  • Lazy-load heavy reference. Don't dump 10K tokens of API docs into SKILL.md. Reference a reference/api.md the body links to.
  • Prefer scripts to inline code. If the skill needs to run something deterministic (parse a PDF, validate JSON), put it in scripts/ and have Claude call it. Reproducibility goes up; token usage goes down.
  • Test the trigger. After writing a skill, ask Claude variations of the expected user prompts and confirm it activates. If it doesn't, the description is wrong.
  • Version when you ship. If teammates depend on the skill, pin a version and bump it on breaking changes.
